# Code Guide — how this app works, in plain English

This document explains what every part of the project does and which languages/
technologies are used. Read it top to bottom and you should be able to find your
way around the whole codebase.

---

## 1. Which languages and technologies are we using?

| Layer | Technology | Where it lives |
| --- | --- | --- |
| Page structure | **HTML5** | `index.html` (every screen and popup is defined here) |
| Styling | **CSS3** (mobile-first, no framework) | `styles.css` |
| All app logic | **Plain JavaScript** (vanilla ES2020+, **no framework**, no npm packages) | `js/*.js` (15 files) |
| Database + login | **Supabase** = hosted **PostgreSQL** database, auth, and Row Level Security | tables defined in `supabase/schema.sql` |
| Database language | **SQL** (table definitions, policies, seed data) | `supabase/schema.sql` |
| Data access from JS | **supabase-js** library (bundled locally) | `vendor/supabase.js` |
| Build step | **Node.js** script (copies files, injects config) | `build.js` |
| Hosting | **Vercel** (builds on push, serves `dist/`) | `vercel.json` |
| Installable on phone | **PWA manifest** + icons | `manifest.json`, `icon-*.png` |

Key point: **the front end is 100% plain HTML/CSS/JavaScript** — no React, no
Vue, no jQuery, no bundler (webpack/vite), no TypeScript. The only third-party
code is the Supabase client library, downloaded and served from `vendor/` so the
app works without any CDN.

---

## 2. The big picture

```
        ┌────────────────────────── browser ──────────────────────────┐
        │  index.html ── defines every screen, modal and button       │
        │  styles.css ── makes it look right on phone + laptop        │
        │  js/*.js    ── all behaviour (load in a fixed order)        │
        └───────────────┬─────────────────────────────────────────────┘
                        │  HTTPS (supabase-js)
                        ▼
        ┌────────────────────────── Supabase ────────────────────────┐
        │  PostgreSQL tables: sales, installments, payments, ...     │
        │  Auth: email/password login                               │
        │  RLS: only a signed-in user may read/write anything       │
        └────────────────────────────────────────────────────────────┘
```

- `npm run build` → runs `build.js` → creates `dist/` (copies the static files
  and writes your Supabase URL/key into `dist/config.js`).
- Vercel runs that same build on every push and serves `dist/`.
- At runtime the browser loads `index.html`, then the scripts, then `boot()`
  checks "am I logged in?" and shows either the login screen or the app.

## 3. How the JavaScript files are loaded (order matters)

`index.html` at the bottom loads them as **classic scripts** (not ES modules),
each one adds its functions to the global scope, so any file can call any other
file's function:

```
vendor/supabase.js   ← the library (defines `supabase`)
config.js            ← generated by build.js (defines `window.ENV`)
js/core.js           ← helpers everyone uses ($, money, toast, modals…)
js/navigation.js     ← `state` (the shared data object) + switchView()
js/auth.js           ← login/session + boot()
js/filters.js        ← shared ⚙ Filters engine
js/items.js          ← shared item picker
js/dashboard.js      ← dashboard screen
js/sales.js          ← sales screen
js/receivables.js    ← To receive screen
js/payables.js       ← To pay screen
js/loans.js          ← loans screen
js/expenses.js       ← expenses screen
js/purchases.js      ← purchases screen
js/zakat.js          ← zakat screen
js/payments.js       ← shared payment sheet
js/main.js           ← wires buttons → functions, then calls boot()  ← MUST BE LAST
```

Why classic scripts instead of ES modules? Because it keeps everything dead
simple: no build/bundle step, no import/export syntax, and any function defined
in any file is callable from any other file. The cost is that load order must be
right — which is why `main.js` (which starts the app) is always last.

Each file starts with a comment block like:

```js
/* ============================================================
   loans.js - money we gave out (personal loans)
   -----------------------------------------------------------
   ...
   PROVIDES: loadLoans, renderLoans, openLoanForm, saveLoan, openLoanDetail
   ============================================================ */
```

`PROVIDES` lists everything that file defines, so you can grep for a function
name and instantly know which file owns it.

## 4. File-by-file: what each one does

### The foundation (read these first)

**`js/core.js`** — the toolbox used everywhere:
- `sb` — the Supabase client (how every query is sent).
- `$()` / `$$()` — short for `document.querySelector` / `querySelectorAll`.
- `esc()` — escapes text so user input can't inject HTML.
- `num() / round2() / money()` — number handling and `Rs 500,000` formatting.
- `fmtDate()` + date helpers (`todayISO`, `monthStartISO`, `addMonths`…) — all
  dates are stored as `YYYY-MM-DD` strings.
- `parseAmount()` — turns `"5l"` → `500000`, `"50k"` → `50000`, `"2million"` →
  `2000000` (units: `k` = thousand, `l` = lac, `million` = 10 lac).
- `toast()` / `busy()` — the little message bubble and the loading spinner.
- `openModal() / closeModals() / askConfirm()` — every popup in the app goes
  through these three.

**`js/navigation.js`** — two things:
- `state` — **the one shared object** where the app keeps whatever it needs
  between renders: loaded rows (`state.sales`, `state.loanRows`…), search-box
  text (`state.expSearch`…), active filters (`state.f`, `state.lf`). If you ever
  wonder "where does this screen keep its data?", it's here.
- `switchView(view)` — hides all `.view` sections, highlights the tab, closes
  popups, and calls that view's loader (the `loaders` map).

**`js/auth.js`** — `boot()` is the entry point (called by `main.js`): it binds
events, reads the Supabase session, and shows the login screen or the app.
`handleSession()` flips between the two; `login()` submits the form.

### The shared engines (used by several screens)

**`js/filters.js`** — one ⚙ Filters engine for six tabs (purchases, loans,
expenses, zakat, To receive, To pay). `LIST_TABS` is a config table saying which
button/panel/search-box belongs to which tab, and `applyListFilters()`,
`listQuickRange()`, `clearListFilters()` do the work. Adding a filter panel to a
new tab = one entry in `LIST_TABS`. (Sales has its own panel, inside `sales.js`.)

**`js/items.js`** — the item picker shared by the Sale and Purchase forms:
one row per machine/item. The machine dropdown, the printer/probe tick-boxes and
typing by hand all feed the same rows (`addNewItem`, `removeItemRow`,
`syncItemChecks`). `PICKERS` just points this code at each form's own element
ids.

**`js/payments.js`** — one payment sheet used by four places: sale, owe entry,
purchase and loan (`openPaymentModal(type, id, context, max)` /
`savePayment`). It writes a row into `payments`; if a loan receives its last
rupee it also stamps `returned_at` on the loan.

### The screens (one file per tab)

| File | Tab | What it does |
| --- | --- | --- |
| `dashboard.js` | Dashboard | Loads the chosen date range and draws the summary cards (`loadDashboard`, `applyRange`). |
| `sales.js` | Sales | The biggest screen: list + ⚙ filters + search (`filterSales`, `renderSales`), the sale detail sheet (`openSaleDetail`), the salesman manager (`openSalesmenModal`), and the New Sale form with its installment schedule (`openSaleForm`, `buildSchedule`, `saveSale`). |
| `receivables.js` | To receive | Joins unpaid sale installments with their payments, lists what's due, flags overdue (`loadReceivables`, `renderReceivables`). |
| `payables.js` | To pay | Owe entries plus any purchase still owing money, in one list (`loadPayables`, `openPayableForm`, `savePayable`). |
| `loans.js` | Loans | Money given out: list with returned/late state, optional return schedule, the detail sheet with schedule + recorded returns (`openLoanDetail`, `setLoanReturned`, `saveLoan`). |
| `expenses.js` | Expenses | Money spent — "Paid to" who + what for (`saveExpense`). |
| `purchases.js` | Purchases | Things bought (batch statement or local item picker), cash/bank/installment payments, balance + status badge (`savePurchase`, `syncPurchaseForm`). |
| `zakat.js` | Zakat | Simple list + form, same pattern as expenses. |

**`js/main.js`** — the wiring diagram. `bindEvents()` maps every button, search
box, form `submit` and ⚙ panel in `index.html` to a function in the files above.
At the very bottom it calls `boot()` to start the app. **This file must load
last** — by then every function it references exists.

## 5. How one action flows through the code (example: saving a sale)

```
1. index.html        <form id="sale-form"> … <button>Save</button>
2. main.js           $("#sale-form").addEventListener("submit", saveSale)
3. sales.js          saveSale(e)              — reads the form fields
                      · parseAmount("5l") → 500000        (core.js)
                      · validates, builds the installment schedule
4. sales.js          await sb.from("sales").insert({...})  (via core.js `sb`)
                     await sb.from("installments").insert([...])
5. sales.js          loadSales()              — re-reads the table
6. sales.js          renderSales()            — rebuilds the list rows
7. core.js           toast("Sale saved")      — confirmation bubble
```

Every screen follows the same rhythm: **read form → write to Supabase → reload →
render → toast**. There is no local caching layer; the lists you see are always
fresh reads from the database.

## 6. Where do I change …?

| I want to… | Touch |
| --- | --- |
| add/rename a field on a form | `index.html` (the input) + the screen's `save*`/`render*` in `js/` |
| change how a list line looks | the `render*` function in that tab's file |
| add a new tab/screen | `index.html` (a `<section class="view">`), a new `js/xxx.js`, add its loader in `navigation.js`, add its script tag in `index.html`, wire buttons in `main.js` |
| change money/date formatting | `js/core.js` (`money`, `fmtDate`, `parseAmount`) |
| change the database | `supabase/schema.sql` (re-run it in Supabase SQL Editor) |
| add a filter to the ⚙ panel | `LIST_TABS` in `js/filters.js` (+ the input in `index.html`) |
| change login/security | `supabase/schema.sql` (RLS policies) + `js/auth.js` |

---

## 7. Build & deploy in one paragraph

`npm run build` runs `build.js`, which deletes `dist/`, copies `index.html`,
`styles.css`, `manifest.json`, icons, `vendor/` and `js/`, and writes
`SUPABASE_URL`/`SUPABASE_ANON_KEY` (from `.env` locally, from Vercel's settings
in production) into `dist/config.js`. `vercel.json` tells Vercel to run exactly
that build and serve `dist/`. That's why you never edit `dist/` by hand — it is
100 % generated.
